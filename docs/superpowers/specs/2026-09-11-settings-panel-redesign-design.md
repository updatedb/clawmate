# 系统设置面板改版设计

## 目标

重做系统设置模态（Rootdir 管理 / 用户管理）的布局与交互。当前版本的问题是结构性的——它同时充当「一份可浏览的清单」和「一个单条目的编辑器」，两者挤在一个 640px 的单列滚动里抢同一块地方，导致读要滚过写、编辑时看不见自己在改哪行。

本设计把这两件事分开：**列表在自己该有的视图里独占高度，编辑器在需要时才出现。**

## 背景：实测确认的缺陷

每条都在真实浏览器中用真实标记 + 真实样式表量过，不是看图推断。它们是改版的依据，也定义了验收标准。

### 1. `.settings-form input` 选择器泄漏到权限复选框（严重）

`dev/static/css/style.css:96` 按**元素名**匹配，命中了 `#settingsUserRoots` 内的 `<input type="checkbox">`。实测（1280px 视口，fieldset 宽 308px）：

| 量 | 实测值 |
|---|---|
| 复选框尺寸 | **308 × 30** |
| 外层 `<label>` 高度 | **54.5px**（标签被挤到方块下一行） |
| `accent-color` | `auto`（UA 蓝，与品牌 teal 不符） |

站内已有正确做法可比照：`style.css:958` `.list-item .list-check { accent-color: var(--accent); }`。

### 2. 行内「编辑 / 删除」是未挂类的 UA 默认按钮（严重）

`dev/static/js/app.js:3224` / `:3237` 用 `document.createElement('button')` 创建且**不赋 className**；全站没有 `button {}` 基类规则，只有 `.btn`。唯一修饰是 `.settings-root button { font-size: 12px; }`。同一模态里的表单按钮用的是 `.btn .btn-primary` / `.btn .btn-secondary`——两套外观并存。附带后果：`删除` 不可逆却与 `编辑` 同权。

### 3. 占位符当标签（严重，可访问性）

`index.html:311-330` 的全部输入只有 `placeholder`，没有 `<label for>`，违反 WCAG 3.3.2。占位符在输入后消失，管理员回头核对「这条 root 的 agent 填的是什么」时无从对照。`#settingsUserRoots` 的 fieldset 有 `aria-label`，是这一片里唯一正确的。

### 4. 两个 tab 的列表行样式分裂

`.settings-user`（`style.css:98`）有 `border-bottom`，`.settings-root`（`:107`）没有。同一模态、同一层级的两个列表，一个有分隔线一个没有。

### 5. 深色模式下自动填充压过主题

全站 **0 处** `-webkit-autofill` 覆盖。实测 `settingsUsername` 是浅底、紧邻的 `settingsPassword` 是深底。

### 6. 删除确认绕开统一模态系统

`style.css` 开头即声明 "Unified Modal System"，而 `app.js:3238` 走 `window.confirm`。视觉与焦点管理都不在同一套里。

### 7. 结构性缺陷（改版的直接动因）

1. **读要滚过写**：想看一眼有哪些 root，必须滚过一张 5 个空输入的表格。
2. **编辑时看不见目标**：点某行「编辑」，表单永远在列表**下方**（6 行之后）。滚下去之后，就看不见自己在编辑哪一行了。
3. **没有「正在编辑哪一行」的反馈**：行不高亮，唯一信号是底部按钮从「创建用户」变成「保存用户」——而那个按钮当时还在屏幕外。
4. **行是一根连成串的字符串**：`Topic Writer · writer/topics · agent:writer` 是三类信息、同一字重、无对齐，没法竖着扫。

## 选定方向

**方向 B：列表优先，表单按需唤出。**

调研了三个方向，结论如下：

| | 方向 | 结论 |
|---|---|---|
| A | 主从（列表左 / 编辑器右，模态放宽到 ~880px） | 否决。为不常发生的行为（编辑）付出永久性的宽度与复杂度代价 |
| **B** | **列表优先（列表独占高度，表单唤出）** | **采用** |
| C | 行内展开（点行就地变编辑区） | 否决。按 10–20 条的规模，展开行会让列表跳动明显、浏览态与编辑态混在同一条滚动流里 |

选 B 的理由是**使用频率**：这个面板的核心动作是**核对**（「我的 root 配对了没」「用户 X 现在能访问什么」），读远多于写。B 把读的路径做到最优——列表独占全高、不滚动就能看全 20 条——同时给写保留了完整的空间。

模态宽度**维持 640px 不变**（`style.css:94` `.settings-modal-box { max-width: 640px }`），这是 B 相对 A 的主要优势。

## 原型

低保证真度，只表达结构、层级与交互，不涉及配色与字体。

### Rootdir 管理 — 列表视图

```
┌──────────────────────────────────────────────────────────┐
│  系统设置                                          [✕]   │
├──────────────────────────────────────────────────────────┤
│  Rootdir 管理      用户管理                               │
├──────────────────────────────────────────────────────────┤
│                                          [+ 新建 Rootdir] │
│                                                          │
│  Topic Writer                                            │
│  writer/topics  ·  agent: writer                         │
│  ────────────────────────────────────────────────────    │
│  Hike Plans                                              │
│  travel/trip  ·  agent: travel                           │
│  ────────────────────────────────────────────────────    │
│  CookBook                                                │
│  homeservice/recipe  ·  agent: home                      │
│  ────────────────────────────────────────────────────    │
│  Debate Arena            已被 2 位用户引用                │
│  .openclaw/debate-arena/archives  ·  agent: main         │
│  ────────────────────────────────────────────────────    │
│  Openclaw Media                                          │
│  .openclaw/media  ·  agent: main                         │
│  ────────────────────────────────────────────────────    │
│  …                                                       │
└──────────────────────────────────────────────────────────┘
```

- 整行是点击目标，进入该条的聚焦表单（Fitts's Law：目标越大越易命中）。不再有行内按钮。
- 行内三级：**显示名**（H2，13px/600/`--text-primary`）→ **目录 · agent**（H3，12px/`--text-secondary`，monospace 呈现路径）。
- 引用计数（`已被 N 位用户引用`）作为行内提示，只在 `N > 0` 时出现；它回答的正是「删了这个会怎样」，所以必须在删除**之前**可见。
- `[+ 新建 Rootdir]` 置于列表右上，与「新建」在同类清单里的惯例一致。

### Rootdir 管理 — 聚焦表单（新建 / 编辑共用）

```
┌──────────────────────────────────────────────────────────┐
│  ← Rootdir 列表                    编辑 Rootdir    [✕]   │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  显示名                                                  │
│  [Topic Writer___________________________________]       │
│                                                          │
│  目录（相对系统根目录）                                  │
│  [writer/topics___________________]      [ 浏览… ]       │
│                                                          │
│  Agent                                                   │
│  [writer__________________________________________]      │
│  id: topic-writer（创建后不可更改）                      │
│                                                          │
│                                                          │
│                                  [ 取消 ]   [ 保存 ]     │
│                                                          │
│  ────────────────────────────────────────────────────    │
│  删除这个 Rootdir                                        │
│  已被 2 位用户引用，删除后这些授权将失效。               │
│  [ 删除 ]                                                │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

- 每个字段有**可见标签**（12px，`--text-secondary`），标签文案沿用现有 placeholder 的文字。站内没有 sr-only 工具类（`css/` 全量检索为空），而可见标签在核对长表单时本来就比占位符有用——这正是要修的场景。
- 目录字段仍 `readonly`，配合「浏览…」——用 HTML 语义表达「这个值只能通过选择器改」。
- `id` 是派生的、创建后不可更改，所以是**说明文字**而非输入框；编辑现有条目时回显实际 id。
- **危险区与保存物理分离**（`proximity` 原则的反向运用：不相关的操作不该相邻），删除不再是和保存等权的按钮。

### 危险区二次确认（替代 `window.confirm`）

```
│  ────────────────────────────────────────────────────    │
│  删除这个 Rootdir                                        │
│  已被 2 位用户引用，删除后这些授权将失效。               │
│  [ 删除 ]                                                │
│                                                          │
│              ↓ 点击后原位展开                             │
│                                                          │
│  ────────────────────────────────────────────────────    │
│  删除这个 Rootdir                                        │
│  已被 2 位用户引用，删除后这些授权将失效。               │
│  确定删除？此操作不可恢复。                              │
│  [ 确认删除 ]   [ 取消 ]                                 │
```

**原位两步确认**，不新建对话框组件：站内没有可复用的确认 API（`.modal-overlay` 只提供容器，`window.confirm` 在 `app.js` 用了 4 处），所以整体替换超出范围；但在这一屏里做一次原位两步确认的成本很低，且能一举解决第 6 项缺陷。用户管理 tab 的删除沿用同一形态。

## 交互说明

| 元素 | 触发 | 动作 | 反馈 |
|---|---|---|---|
| 列表行 | 点击 / Enter | 进入该条的聚焦表单 | 行短暂高亮后切视图 |
| `[+ 新建 …]` | 点击 | 进入空白聚焦表单 | 标题为「新建 Rootdir / 用户」 |
| `← …列表` | 点击 | 返回列表视图 | 保留列表滚动位置 |
| Tab | 点击 | 切换 tab，**并复位到列表视图** | 下划线指示器移动 |
| `[保存]` | 点击 | 提交 | 按钮进入 pending，成功后回列表并刷新该行 |
| `[取消]` | 点击 | 放弃改动 | 有未保存改动时二次确认 |
| `[删除]` | 点击 | 原位展开二次确认 | 不跳转、不弹窗 |
| `[确认删除]` | 点击 | 执行删除 | 成功后回列表 |
| `[浏览…]` | 点击 | 打开现有目录选择器 | 仅 `dir` 字段可见 |

**视图状态**：模态体内有 `list` / `form` 两个视图，由单一状态变量驱动；切换 tab 复位为 `list`。表单视图有「新建」与「编辑」两种模式，共用同一组字段，仅标题与提交动词不同——这是**已知的取舍**（见「假设与风险」）。

**渐进披露**：危险区常驻可见（不藏在菜单里），但破坏性动作需要第二次点击才生效。

## 状态

**空状态**（列表无条目）：

```
│                                                          │
│              还没有 Rootdir                              │
│       Rootdir 是用户可访问的根目录，至少需要一个才能      │
│       创建普通用户。                                     │
│                                                          │
│               [+ 新建 Rootdir]                           │
│                                                          │
```

空状态必须解释**为什么需要它**并给出下一步动作，而不是只显示「暂无数据」。

**错误态**：保留模态外壳与 tab，错误出现在 `#settingsError`（`role="alert"`，现状已有），并提供「重试」。

**加载态：明确不做。** 设置列表的数据来自本机 API，实测瞬时返回，骨架块会引入一个永远看不到的中间态。原设计曾把「与行同形的 3 行骨架」列入范围，实现计划的自查发现无人实现——判定为**范围外的多余要求**，从这里移除而不是补一个任务去满足它。

## 实现映射

新增类一律遵循 `AGENTS.md` 的「kebab-case + surface prefix + BEM-lite」，尺寸走 `tokens.css`，不新增魔法值。

| 区域 | 类 / 元素 | 说明 |
|---|---|---|
| 视图容器 | `.settings-view[data-settings-view="list\|form"]` | 与既有 `data-settings-panel` 的写法一致 |
| 列表 | `.settings-list` | 两个 tab 共用 |
| 行 | `.settings-row`（`.settings-row-title` / `.settings-row-meta`） | 取代 `.settings-root` / `.settings-user` |
| 勾选网格 | `.settings-grants`（内含 `label > input[type=checkbox]`） | `display: grid; grid-template-columns: 1fr 1fr` |
| 危险区 | `.settings-danger` | 内含 `.settings-danger-confirm[hidden]` |
| 返回 | `.settings-back` | 复用 `.btn` 家族 |

必须同时修掉的既有选择器问题：

```css
/* style.css:96 —— 排除复选框：一行控件的尺寸规则不该跨控件类型套用 */
.settings-form input:not([type="checkbox"]) { /* …原声明… */ }

/* 复选框回到自然尺寸，并对齐 style.css:958 既有的 accent-color 用法 */
.settings-grants input[type="checkbox"] { width: auto; min-height: 0; padding: 0; margin: 0 6px 0 0; accent-color: var(--accent); }

/* 自动填充跟随主题 */
.settings-form input:-webkit-autofill,
.settings-form input:-webkit-autofill:hover,
.settings-form input:-webkit-autofill:focus {
  -webkit-box-shadow: 0 0 0 1000px var(--bg-primary) inset;
  -webkit-text-fill-color: var(--text-primary);
  caret-color: var(--text-primary);
}
```

JS 侧：`app.js` 里 `createElement('button')` 生成的行内按钮**全部**改挂 `.btn btn-secondary`（删除另加 `.danger`），并移除 `.settings-root button { font-size: 12px; }` 这条唯一的样式兜底。

## 范围

**包含**：第 1–7 项全部；列表/表单双视图、统一行结构、勾选网格、危险区原位二次确认、可见标签、自动填充覆盖、空/错误态、移动端布局。

**不包含**：

- **站内通用的确认对话框组件**。本设计只在设置面板内做原位两步确认。`window.confirm` 在 `app.js` 共 4 处，其中设置面板占 2 处（`:3201` 删 Rootdir、`:3241` 删用户，本次修掉），另 2 处（`:283` 批量删除、`:701` 删文件）**保持原样**。
- **创建 / 编辑拆成两个表单**。当前共用一组字段、仅标题与动词不同。是否需要拆开取决于真实使用数据（管理员以创建为主还是以编辑为主），不是设计原则能定的。

## 假设与风险

**假设待验证**

1. 读远多于写——B 的全部理由建立在此之上。若实际是频繁连续编辑，A 的心智成本更低。
2. root 规模 10–20 个。**两列网格在 24 个以内都能撑住**（12 行）；超过就该换成「搜索 + 已选 chips」，这是本设计明确不覆盖的规模。

**风险**

1. **双视图引入状态**：「当前在哪个视图 / 编辑哪一条」需要在切 tab、刷新、出错时都保持一致。缓解：单一状态变量 + 切换 tab 强制复位，并用 e2e 覆盖「切 tab 后不残留在表单视图」。
2. **列表滚动位置**：从表单返回时若不保留，会退回「找不到刚才那行」的老问题。缓解：返回前记录并恢复 `scrollTop`，e2e 断言。
3. **类名可以换，ID 必须保**。已查证：`tests/test_settings_frontend_contract.py` 与 `tests/test_e2e_browser.py` 引用的是 **ID 而非类名**（`settingsRootDir` / `settingsRootBrowse` / `settingsRootAgent` / `settingsUserRoots` / `settingsTabRoots` / `settingsTabUsers` 等）。所以 `.settings-root` → `.settings-row` 的替换不会碰测试，但**上述 ID 一个都不能改**——`#settingsUserRoots` 在 `test_e2e_browser.py:696` 有可见性断言，`#settingsRootBrowse` 在 `:629` 有点击，`test_settings_frontend_contract.py` 还从 `app.js` 里按 ID 抽取事件处理函数体做断言。改版重排 DOM 时必须原样保留这些 id 与 `data-settings-panel` / `data-settings-tab` 属性。
4. **空状态文案提到「至少需要一个才能创建普通用户」**——这条规则由 `user_store.create_user` 强制（`普通用户至少需要一个授权 Rootdir`），文案必须与代码保持一致，否则管理员会困惑于为什么建不了用户。
